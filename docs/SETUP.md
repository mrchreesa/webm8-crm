# Owner setup and deployment

## Meta account-side setup

1. **App and lead access.** Associate a Meta app with your business. Use a Page access token with `leads_retrieval`, and grant the relevant person/system user Page, ad-account and Leads Access Manager permissions. Page subscription typically needs `pages_manage_metadata`; Page discovery may need `pages_show_list` and `pages_read_engagement`. App review/advanced access/business verification requirements depend on your app's access and users. Confirm the current permission requirements in your own developer dashboard. [Meta lead retrieval guide](https://developers.facebook.com/docs/marketing-api/guides/lead-ads/retrieving/).
2. **Public HTTPS webhook.** Put the CRM behind HTTPS. Set `APP_URL` to that origin, `META_PAGE_ID` to the exact Page string, and strong random `META_VERIFY_TOKEN` and your app's `META_APP_SECRET`. In the app's Page webhook setup, use `https://your-crm.example/api/webhooks/meta`, subscribe to `leadgen`, and subscribe the specific Page to the app (Page `subscribed_apps` with `subscribed_fields=leadgen`, using authorised Page access). Verification alone does not subscribe the Page. [Meta webhooks](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/).
3. **CRM dataset and token.** In Events Manager, create/select the dataset intended for CRM outcomes and follow the available Conversions API / CRM connection flow. Interface names differ by account. Grant the CAPI token holder access to that dataset. Set `META_CAPI_ACCESS_TOKEN` server-side and enter the exact dataset ID in Integration (or seed it with `META_DATASET_ID` before any settings save). The code POSTs to `https://graph.facebook.com/{version}/{dataset_id}/events`. [Meta CRM integration guide](https://developers.facebook.com/docs/marketing-api/conversions-api/guides/conversions-api-for-crm/).
4. **Genuine test lead.** Set `META_TEST_EVENT_CODE` from Events Manager → Test Events. Restart web and worker, then select Meta test mode before creating a lead for your actual Page/form in the [Lead Ads Testing Tool](https://developers.facebook.com/tools/lead-ads-testing/). Ensure New arrives in Test Events, then record actual Contacted/Qualified/Booked/Won or unsuccessful outcomes and inspect delivery. The original lead ID should be an exact string in the record. Check Sync log and Events Manager diagnostics. Demo/manual records cannot validate the integration. Leads received in test mode remain test-only. A live-origin lead can send test-mode milestones without promotion of those test events.
5. **Sales funnel and positive stages.** Configure Meta's CRM funnel using the application event names (`CRM_NewLead`, `CRM_Contacted`, `CRM_Qualified`, `CRM_AppointmentBooked`, `CRM_Won`, `CRM_Lost`, `CRM_Unqualified`). Complete any validation/history/volume requirements shown by Meta. Positive optimization stages are **Qualified, Appointment Booked or Won**, based on your business. **Contacted, Lost and Unqualified are not positive qualification targets.** Initial receipt is not automatic qualification. Send genuine unsuccessful outcomes too. Do not invent skipped stages or turn every stage into Purchase.
6. **Ad-account dataset access.** Assign the intended ad account to the dataset in Business Settings/Events Manager and grant the necessary user/system-user permissions. Events sent successfully do not assign the dataset to an ad account.
7. **Explicit live mode.** Review the dataset, test results and credentials; select Live, check the explicit enable-live confirmation and save. Existing demo/test payloads stay in their original mode. Rotate tokens in environment variables and restart both services. Retry recoverable events within seven days. Corrections cannot retract accepted events.
8. **Advertising setup.** In Ads Manager, use Leads + Instant Forms and select the **Conversion Leads** performance goal when available and suitable for your account/dataset/funnel. Complete the ad set and funnel setup in Meta. Availability, validation and optimization eligibility are account-side decisions; this application cannot finish them merely by sending events. [Meta's lead generation guide](https://about.fb.com/ltam/wp-content/uploads/sites/14/2023/11/LeadGenerationGuide.pdf).

Graph version is configurable with `META_GRAPH_VERSION`. Default `v26.0` was verified against [Meta's official Node SDK](https://github.com/facebook/facebook-nodejs-business-sdk/blob/main/src/api.js) and the signed-in Events Manager CRM implementation guide on 3 October 2026; review [the Graph changelog](https://developers.facebook.com/docs/graph-api/changelog/) before upgrades. Direct documentation fetches were rate-limited. The current guide links to [Implementing the CRM integration](https://developers.facebook.com/docs/marketing-api/conversions-api/conversion-leads-integration/crm-integration/3-implementing-the-crm-integration). Signed webhook intake, real lead retrieval and two initial CAPI events have now been verified in Meta test mode; see [the verification report](VERIFICATION.md). Live delivery and ordinary customer submissions remain separate checks.

## Persistent deployment

The CRM currently uses Neon PostgreSQL on its Free plan in AWS London, while web and worker still run on the Mac. See [Neon migration and hosting](NEON.md). The following deployment option also supports local SQLite.

Use a single persistent Linux server or container host. SQLite WAL needs a local durable disk; do not use an ephemeral serverless filesystem, network filesystem or two separate disks for web/worker.

1. Copy this project, run `npm ci`, then `npm run setup -- --email your-email@example.com`. Keep the generated password securely and rotate local demo owner access before deployment.
2. Update `.env`: `APP_URL=https://crm.your-domain.example`, `TRUST_PROXY=1` **only** if there is exactly one trusted reverse proxy, and Meta configuration. Keep the file readable only by the service account. For containers, inject the same variables into both services. Do not commit them.
3. Run `docker compose up --build -d`. The named `crm-data` volume is shared by web and worker. Both have restart policies and health checks. Migrations are applied at startup. The web port binds only to localhost.
4. Configure your existing reverse proxy with HTTPS to localhost:3001. `deploy/Caddyfile.example` shows the mapping if you use Caddy; equivalent nginx/host-proxy configuration works. Point DNS at the host. Do not expose port 3001 directly to the internet.
5. Confirm owner login, webhook callback verification and Integration → worker heartbeat. Stop/restart the web container and confirm the same leads still appear. The worker remains active when the browser is closed.
6. Configure backups of the durable volume using SQLite online backup, encrypt/access-control them, and test restoration. Deleting a lead in the app does not erase external backups or events previously accepted by Meta. See ARCHITECTURE.md.

Without containers: run `npm ci && npm run build && npm run migrate`, then supervise `npm start` and `npm run worker` as separate services with the same environment, service user, working directory and absolute `DATABASE_PATH` for SQLite, or the same server-side `DATABASE_URL` for PostgreSQL. Configure automatic restarts, monitor heartbeat/delivery errors, and put the API behind HTTPS. Do not run only the web process.

The demo seed is optional (`npm run demo`) and idempotent. Synthetic records are marked demo and never dispatched, even when Live is enabled. The owner can switch between Your leads and Demo data without mixing their dashboard counts.

## Historical CSV imports and exports

Select UTF-8 CSV, map columns and preview. Import up to 2,000 records / 1 MB. Require `name` and original `received_at`; Meta imports also require exact `meta_lead_id`, `page_id`, `form_id`, `meta_submitted_at`. Manual source remains integration-ineligible. Contact phone can be local UK or explicit international; invalid matching phone values are omitted from CAPI.

Current stage defaults to New. For another current stage, supply its actual milestone date (`contacted_at`, `qualified_at`, `appointment_booked_at`, `won_at`, `lost_at`, `unqualified_at`). Map only milestones that really occurred, in chronological order; the current stage must be the latest supplied milestone. `new_at` defaults to original receipt, never the import time. Booked requires `appointment_at`; Won requires `sale_gbp`; Lost/Unqualified require `reason`. Dates must include an offset or Z. Blank/invalid dates are not replaced with now. Uploads older than seven days are marked Expired.

Duplicate Meta IDs are skipped, even with different email values. Matching emails do not merge distinct submissions. A committed identical CSV/mapping/source returns the prior summary if submitted again; invalid rows remain available in the summary. To fix them, upload a corrected file. No file content is retained outside the saved lead data.

CSV export quotes exact digit IDs. **Open it through your spreadsheet's import flow and set every Meta ID column to Text**, rather than double-clicking; quoting alone cannot prevent Excel/Sheets numeric auto-detection. Use authenticated `/api/leads/export?format=json` for a complete precision-safe archival export including history, notes and events. Personal fields that could become spreadsheet formulas are neutralised in CSV.
